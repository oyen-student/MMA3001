# DTMB 5415 Hull-Resistance Prediction (MMA3001)

This repository compares simple regression baselines with a PyTorch multilayer perceptron (MLP) for predicting a selected row of `coefStatMatrix` from the DTMB 5415 hull parameter matrix.

`mma3001.data_prep` uses zero-based Python row indices. The `metadata.txt` included in the dataset archive maps `coefStatMatrix` rows 1-3 to model-scale wave-resistance coefficient (`Cw`) at Froude numbers 0.25, 0.33, and 0.41. Thus `--target-row 0` means `Cw` at Fr=0.25, according to that metadata. The result JSON records this definition and its source. The 27 inputs remain normalized design variables; individual variable meanings and units are not established by the metadata inspected here.

## Pipeline

- `src/mma3001/data_prep.py`: validates MAT-file keys/shapes and finite values; creates reproducible random sample-level train/validation/test splits; fits feature and target standardisers on training data only; records the target-row definition; and audits exact duplicate design vectors across splits.
- `src/mma3001/linear_regression.py`: mean-target sanity baseline and linear-regression baseline.
- `src/mma3001/neural_network.py`: PyTorch MLP, reproducible training, post-epoch train/validation loss measured in evaluation mode, configurable gradient clipping, pre-clipping gradient-norm diagnostics, early stopping, best-checkpoint restoration, regression metrics, and diagnostic plots.
- `src/mma3001/hyperparameter_tuning.py`: Optuna TPE search over MLP architecture, learning rate, weight decay, and batch size using validation MSE in original target units.
- `src/mma3001/main.py`: complete experiment, held-out test evaluation, and output saving; run it with `python -m mma3001`.
- `requirements.txt`: Python dependencies.

For the module map, data/model-selection boundaries, training lifecycle, and
Mermaid flow charts, see [ARCHITECTURE.md](ARCHITECTURE.md).

## Run the pipeline

Once the dataset is in the location above, the program finds it automatically. Run the pipeline with Optuna tuning:

```bash
python -m mma3001 --target-row 0 --trials 20
```

Training uses a maximum of 1,000 epochs per model and stops early if validation loss does not improve by at least `--min-delta` for 100 consecutive epochs. This larger budget lets training continue longer before early stopping; the final weights still come from the epoch with the lowest qualifying validation loss. Gradient clipping defaults to a global norm of 1.0; set `--grad-clip 0` to disable clipping. Adjust these settings with `--epochs`, `--patience`, `--min-delta`, and `--grad-clip`; for example:

```bash
python -m mma3001 --target-row 0 --trials 20 --epochs 1500 --patience 150 --min-delta 1e-6 --grad-clip 1.0
```

For a controlled outlier-influence comparison, `--exclude-training-sample` takes a zero-based source sample index and omits it from the training partition after the seeded split is made. Validation and test membership stay the same, so a sample already assigned to either partition cannot be excluded with this option. Use `--comparison-label` to put a clear condition label on the figures. For example, paired runs can retain the point in one output folder and exclude it from training in another:

```bash
python -m mma3001 --target-row 0 --trials 20 --sweep --comparison-label "Sample 3787 included" --output-dir outputs/sample_3787_included
python -m mma3001 --target-row 0 --trials 20 --sweep --exclude-training-sample 3787 --comparison-label "Sample 3787 excluded from training" --output-dir outputs/sample_3787_excluded
```

These runs keep the same validation and test samples and retune each training condition independently. The exclusion run is a sensitivity analysis; it does not establish that the source observation is erroneous or justify deleting it from the scientific dataset.

### Architecture sweep and Optuna tuning

These are two distinct kinds of model-selection work. In the CLI, `--sweep` runs an architecture comparison on the **training and validation partitions**. It trains ten preset hidden-layer layouts using the same default learning rate, weight decay, and batch size, ranks them by validation MSE, and writes `architecture_sweep.csv` and `architecture_sweep.png`. It prints the best sweep architecture, but does not pass that architecture into the final model configuration.

Optuna (enabled by default) searches a broader MLP configuration: one to three hidden layers, layer widths, learning rate, weight decay, and batch size. `--trials` controls the number of configurations trained. The best Optuna configuration is then trained again and used for final evaluation. `optuna_convergence.png` shows each trial's validation objective and the best score so far; it documents the search, but does not establish that the search found a global optimum or fully converged.

The sweep and Optuna both train MLPs and both search architecture choices. The sweep tests ten preset architectures while holding optimizer settings fixed. Optuna searches architecture and optimizer settings together. Running both is supported, but adds the sweep's ten training runs before Optuna and its final refit. The sweep result remains a diagnostic and does not change the Optuna-selected or fixed final model. For normal tuning, Optuna alone is usually sufficient.

To run the architecture sweep without Optuna, add both `--sweep` and `--skip-tuning`:

```bash
python -m mma3001 --target-row 0 --sweep --skip-tuning
```

To run Optuna and the architecture sweep in the same experiment:

```bash
python -m mma3001 --target-row 0 --trials 20 --sweep
```

To run only the fixed default MLP and skip Optuna, use:

```bash
python -m mma3001 --target-row 0 --skip-tuning
```

### Reuse an optimized configuration

An Optuna run automatically saves its selected hyperparameters and experiment context to `best_config.json` in the output directory. Reuse that configuration on a later run to skip the Optuna search:

```bash
python -m mma3001 --target-row 0 --trials 20
python -m mma3001 --target-row 0 --reuse-config outputs/best_config.json
```

The reuse option checks the dataset path, file size and modification time, target row, random seed, sample/feature counts, and split fractions. If these do not match the saved search context, the program stops and asks for a matching configuration or a new search. The cached file keeps the selected architecture, learning rate, weight decay, and batch size. Reusing it skips hyperparameter optimization, but still trains the final MLP, evaluates it, and regenerates outputs; it does not reuse saved model weights. Use `--skip-tuning` when you specifically want the fixed default configuration instead.

**Neither the architecture sweep nor Optuna uses the held-out test partition to choose configurations.** Both use validation results. The held-out test set is evaluated afterward for final reporting; do not use its metrics to pick between sweep, Optuna, or fixed-model results.

### Runtime reporting and reducing run time

Each run prints elapsed wall-clock time for data loading/preprocessing, the optional architecture sweep, baseline fitting and validation, Optuna search, the final MLP fit, held-out evaluation, diagnostic plots, metrics-file writing, and the complete run. `metrics.json` records the stage timings up to the start of its own write. When a sweep runs, each architecture's training time is included in `architecture_sweep.csv`; during Optuna, each completed trial prints its validation score and runtime, and per-trial times are recorded in `metrics.json`.

Optuna's objective uses the best validation MSE already measured during training. Since the target was standardized, multiplying that scaled MSE by the square of the training target scaler's scale gives the same MSE in original target units. This avoids a separate validation prediction pass for every trial while preserving the objective used to rank configurations.

The largest practical runtime reduction is to avoid stacking the ten-architecture sweep on top of Optuna: use Optuna alone for general tuning, and run the sweep when a fixed architecture comparison is useful. For a faster exploratory run, request fewer trials or a lower epoch cap (for example, `--trials 5 --epochs 150`); early stopping may shorten individual fits further. Record these settings when comparing experiments, since reducing search or training budgets can change which configuration is selected and how well it is optimized.

Install runtime and test dependencies:


From the repository root, parse project Python files without writing bytecode, then run pytest:

```bash

python -m pytest -q
```

Pytest stores temporary test files in the ignored `.pytest-tmp/` directory in the repository. This keeps the suite usable in managed Windows environments where the default user temporary directory may be inaccessible.

The tests cover target-row bounds and metadata, mismatched MATLAB array dimensions, NaN/infinity rejection, train-only scaler fitting with an extreme held-out outlier, exact duplicate detection across splits, Optuna trial validation, the MLP training/prediction interface, known-value regression metrics, the deprecated loader's missing-file behavior, CLI input validation, and a short end-to-end CLI smoke test. GitHub Actions is configured to run these checks on pushes and pull requests. A passing synthetic-data test suite checks core software behavior; it does not validate the real MAT file or independently establish the correctness of its metadata.

## Outputs

The output directory defaults to `outputs/` and contains:

- `metrics.json`: train, validation, and held-out test MSE, RMSE, MAE and R-squared; executed command and Python version; dataset/output paths; target-row definition and source; split fractions and sample counts; seed; training/tuning settings; selected configuration; and exact-duplicate audit counts.
- `best_config.json`: selected Optuna hyperparameters, validation objective, tuning settings, and context checks for later reuse (written after a successful Optuna search).
- `training_loss.png`: training loss measured after each epoch's updates, through the early-stopping point. It labels the stopping epoch separately from the checkpoint epoch: the final model restores weights from the epoch with the lowest qualifying validation loss. Validation loss remains part of model selection but is not plotted here.
- `gradient_norms.png`: mean and maximum minibatch gradient norms before clipping, to help diagnose unstable optimisation.
- `architecture_sweep.csv` and `architecture_sweep.png`: actual training/validation errors for the optional architecture sweep.
- `test_predictions.png`: held-out actual-versus-predicted plot. Its dashed diagonal is a 1:1 reference (`actual = predicted`), not a fitted regression or MLP curve.
- `train_validation_predictions.png`: predictions from the final MLP refit using the selected Optuna configuration (the fresh search winner or a reused saved winner). The title identifies the configuration source and settings. The left panel includes every training and validation observation across the full target range; the right zoom makes the dense central region easier to inspect and reports shown/total counts. Training points are in-sample; validation informs early stopping and may inform tuning, so the held-out test results remain the final performance estimate.
- `linear_regression_predictions.png`: standalone held-out actual-versus-predicted plot for the linear regression baseline.
- `linear_regression_training_predictions.png` and `linear_regression_validation_predictions.png`: standalone actual-versus-predicted plots for the linear regression baseline on the training and validation splits. Dashed diagonals show the 1:1 reference, not the fitted linear-regression function. `metrics.json` reports linear-regression metrics separately for all three splits.
- `test_model_comparison.png`: linear-regression and MLP predictions on the same held-out actual-versus-predicted plot, with R-squared and RMSE in the legend.
- `test_residuals.png`: held-out residual plot.
- `runtime_breakdown.png`: elapsed time by pipeline stage alongside total elapsed time before final summary graphics and metrics writing.
- `plots_montage.png`: labeled montage of the run's training, tuning, validation, test, baseline comparison, residual, and runtime plots.
- `optuna_convergence.png`: validation-objective search history (when tuning is enabled).
- Runtime details: stage timings are printed in the terminal; `metrics.json` records stage timings through the start of its own write and the elapsed time for each Optuna trial.

## Methodological safeguards

1. **No preprocessing leakage:** feature and target scalers are fitted on the training split only.
2. **Validation for model selection:** validation data is used for early stopping and Optuna selection; it is not used as the final performance estimate.
3. **Held-out test:** the test split is evaluated after model selection. Do not use test results to choose the architecture or tune hyperparameters.
4. **Loss accounting:** training loss is measured after epoch updates with the model in evaluation mode. Validation loss is still calculated for early stopping and checkpoint selection, but the training-loss figure omits its curve for readability.
5. **Gradient diagnostics:** gradient norms are recorded before clipping; clipping can reduce extreme updates but does not diagnose or eliminate data issues.
6. **Consistent metrics:** model comparisons use MSE, RMSE, MAE and (R²), all calculated in the target's original units.
7. **Reproducibility:** the train/validation/test split and PyTorch/Optuna sampling use fixed seeds by default.
8. **Interpretation limits:** this implementation uses a random sample-level split and reports exact duplicate design vectors crossing partitions. Near duplicates are not measured because there is no justified tolerance, and no hull-family labels are available for a group-aware split. The score estimates performance on this split, not necessarily on genuinely unseen hull families.
